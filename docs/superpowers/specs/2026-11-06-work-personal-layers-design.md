# Work / personal config layers — design

OUT OF DATE

## Intent and why

This repo holds dotfiles for several computers: a work Mac (employer: Dimer Health), a personal Linux laptop (`sLaptop2`), and a personal Mac arriving soon (`sMac02`). Today everything lives in one flat set of directories and gets symlinked unconditionally on every machine by Dotbot. Work-specific things (Bedrock, Atlassian/Figma MCP permissions, ticket-based skills, Flutter paths) sit next to personal things (i3, polybar, ssh hosts) and shared things (zsh plugins, prettier). The only machine-specific layer is an untracked `~/.zshrc.local`. Goal: make the split explicit, keep as much as possible in git for version control, and keep secrets out of git by storing them in Bitwarden. The tooling decision made during design is to replace Dotbot with chezmoi and to use Bitwarden (the official `bw` CLI) as the secret store.

## Goals

- Every file in the repo has one clear applicability: everywhere, one OS, one group (work or personal), or one machine.
- A machine's configuration is chosen by a few values chezmoi stores once on that machine (group and machine name; OS is detected), not by editing the repo per machine.
- OS differences (Linux vs macOS) are handled automatically by chezmoi data and by runtime checks in shell code, not by hand-written conditions per entry.
- Work and personal setups can differ in any file (git identity, ssh hosts, Claude settings, VS Code settings) without affecting each other.
- A dry run shows exactly what would change on a machine before anything is written, and live files that were edited outside the repo are noticed before they are overwritten.
- The layout, the layering rules, and the edit-then-apply workflow are documented clearly (README + CLAUDE.md), because repo edits are no longer live through symlinks.

## Non-goals

- Not a general multi-user or multi-employer framework. The structure should allow a second employer or machine, but nothing is built speculatively for it.
- Not building secret storage or encryption tooling. Bitwarden is the store; the repo only contains templates that read from it.
- Not a rewrite of individual configs (i3, polybar, p10k, etc.). Files move; their contents change only where needed to remove hardcoded paths, split machine-specific bits out, or turn them into templates.

## Anti-goals (would count as failure even if it technically works)

- Secrets (API tokens, Atlassian token, AWS keys) end up committed, or end up rendered into a tracked file.
- Applying on one machine breaks or silently overwrites another machine's setup.
- Live config silently drifts from the repo again (as `~/.claude/settings.json` did).
- A new machine cannot be set up by installing chezmoi and Bitwarden's CLI, running `chezmoi init`, unlocking the vault, and applying.
- The cutover loses any live content on this Mac or on `sLaptop2` with no way back.

## Decisions made with the user

### Archive of the old design

The pre-migration state is preserved on GitHub as branch `v1` and tag `v1_last`, both pointing at commit `0e1028c` (already pushed). Rollback and "copy something from the old layout" both use these. The archive is public and unrewritten (see "Git history").

### Tooling: chezmoi + Bitwarden

Dotbot (and its submodule) is removed. Alternatives considered and rejected: a wrapper that builds a Dotbot config from layer manifests (hand-built resolver, dry-run, and drift detection; the user found it hacky), rcm, yadm, GNU Stow, dotdrop, Nix home-manager. Chezmoi was chosen because dry-run (`apply -n`, `diff`), drift detection against what it last wrote, JSON merging in templates, OS data, once-only file creation, run scripts, and Bitwarden integration are built in. Accepted costs: chezmoi writes real files, not symlinks, so editing the repo no longer changes the live config until `chezmoi apply` is run; and the layer directories become data and conditions rather than overlay directories, because chezmoi maps one source tree to target paths.

Bitwarden access uses the official `bw` CLI (chosen over the unofficial `rbw` for being first-party, accepting the "unlock ritual"): each shell that runs `chezmoi apply` or `diff` needs `export BW_SESSION=$(bw unlock --raw)`, and `bw sync` after adding items. Every apply or diff needs the vault unlocked because secret templates render at apply time. Claude cannot unlock the vault; if it should run a full apply, the user must start the session from a shell that has `BW_SESSION` exported; otherwise Claude uses `dotapply --headless` (see "Install and the apply wrapper"), which needs no vault. The docs must say this. `bitwarden.unlock = "auto"` must NOT be set in the chezmoi config: it makes chezmoi run `bw unlock` itself when `BW_SESSION` is unset, which contradicts the "abort if `BW_SESSION` is unset" policy in "Secrets".

### Repo layout

```
dotfiles/
├── .chezmoiroot            contains "home": chezmoi's source is home/ only
├── install.sh              replaces ./install: installs chezmoi and the bw CLI, then runs `chezmoi init --apply`
├── README.md  CLAUDE.md  docs/
├── assets/                 binary resources, sorted into subfolders by type; never applied, referenced by path
│   ├── images/             fox images, wallpapers, lock-screen image
│   └── audio/              ding.wav
├── archive/                dead tools; never applied
├── templates/              starter files (README, gitignore, env, claudeignore) copied into projects on demand; repo-only, never applied; read through DOTFILE_REPO_PATH
├── layers/                 merged fragments, grouped by layer (top-level and visible by user decision)
│   ├── shared/             claude/settings.json  vscode/settings.json  zsh/env.zsh ...
│   ├── macos/  linux/
│   ├── work/Dimer_Health/  (and wMac01/ inside it)
│   └── personal/           (and sLaptop2/, sMac02/ inside it)
└── home/                   the chezmoi source tree, named after the target paths
    ├── .chezmoi.toml.tmpl      prompts once for group and machine, records os/group/machine as data
    ├── .chezmoiignore          templated filter: which whole files apply on this os/group/machine
    ├── .chezmoiexternal.toml   oh-my-zsh, plugins, p10k (replaces the submodule and omz-install step)
    ├── .chezmoitemplates/      shared templates, including the JSON merge
    ├── .chezmoiscripts/        run scripts (Firefox profile, migration)
    └── dot_*, private_*, ...   files named after their targets
```

Each machine reads four layers; a more specific layer overrides a less specific one, in this order: `shared` → OS layer (`macos` or `linux`, from detected OS) → group layer (`work/Dimer_Health` or `personal`) → machine layer (`work/Dimer_Health/wMac01`, `personal/sLaptop2`, `personal/sMac02`). The group and machine values are chezmoi data stored in `~/.config/chezmoi/chezmoi.toml` (written from the prompts in `.chezmoi.toml.tmpl`); the layer directory for a machine is built from them (`layers/<group>/<machine>`). The OS comes straight from chezmoi's built-in `.chezmoi.os`; there is no override. Found in testing: `.chezmoi.os` is `darwin`, not `macos`, so the merge template must map `darwin` to the `macos` layer directory or the OS layer is silently skipped. Group and machine layers have no OS subfolders: a machine runs exactly one OS. The group/machine split is NOT OS-specific: a personal Mac and a work Mac are both macOS and have different group and machine layers.

Source-tree facts the layout relies on (checked against the chezmoi v2.74.0 docs and by running it in a sandbox on 2026-11-06: a throwaway repo with `.chezmoiroot`, a fake `HOME`, a scratch `--destination`, and a temporary `--persistent-state`, all under `/tmp`). `.chezmoiroot` is read first and its path is relative to the source directory, so root-level files such as `.chezmoi.toml.tmpl` must live inside the new root (matches the layout above). With `.chezmoiroot` set and `--source <repo>`, `.chezmoi.sourceDir` is `<repo>/home` and `.chezmoi.workingTree` is `<repo>` (the git root), so `include` and `stat` with an absolute path like `{{ .chezmoi.workingTree }}/layers/shared/claude/settings.json` work and a `.chezmoitemplates/layers/` fallback is not needed. `stat` returns false for a missing path. `--source` is NOT remembered after `chezmoi init`: later commands fall back to `~/.local/share/chezmoi` unless `sourceDir` is set in `chezmoi.toml`, so the config template must set it (see "Migration and rollback"). `chezmoi init --promptString group=work/Acme` answers `promptStringOnce` non-interactively.

Two mechanisms express a layer. Whole files that apply to only some machines live in `home/` under their target name and are filtered by a templated `.chezmoiignore` (for example `{{ if ne .chezmoi.os "linux" }}.config/i3{{ end }}`, or the `parse-logs` skill ignored unless group is work). Files whose content differs by layer (Claude `settings.json`, VS Code `settings.json`, git config, the zsh env, polybar overrides) are templates in `home/` that read fragments from `layers/<layer>/...` in the order above. Everywhere this spec says a file belongs to "`shared/`", "`macos/`", "`linux/`", a group, or a machine, it means this: no ignore rule, an OS ignore rule, a group ignore rule, or a machine ignore rule on the `home/` file, or a fragment in the matching `layers/` directory.

`.chezmoiignore` is always a template, matches target paths (not source names), allows per-subdirectory files and `!` negation, and excludes win over includes. Organization (settled): one file, with the rules grouped in the same order as the layers (OS, then group, then machine) under a comment header per section, and each section is a single `{{ if ... }}` block that lists the target paths to ignore, so a path appears once and a reader can answer "why is this not applied here" by finding its section. Conditions are written as "not this OS/group/machine" (for example `{{ if ne .chezmoi.os "linux" }}`), so a new machine needs no edits unless it has its own exclusions. Target paths are written relative to `~` and grouped by tool inside a section, never by file type.

Run scripts live in `.chezmoiscripts/` (the documented location) and may be `before_` or `after_`. `run_once_` and `run_onchange_` are keyed on the SHA256 of the rendered script content, not the filename, so editing a script (even adding a comment) re-runs it, changing data that feeds the hash in a `run_onchange_` template re-runs it, and an empty render is skipped. Verified by running: `run_once_before_` and `run_onchange_after_` scripts run once and not on an unchanged re-apply. Scripts are NOT executed in dry-run (`apply -n`), and they run with the real `HOME` of the invoking environment, not a scratch destination (see "Migration and rollback" for what that means when verifying).

External downloads (oh-my-zsh, plugins, p10k) cannot be pinned with `git-repo` externals in `.chezmoiexternal.toml`: they have only `clone.args` and `pull.args`, no ref field, and an existing clone is updated with `git pull`. To pin them, use `type = "archive"` with a tag or commit tarball URL and `checksum.sha256`.

### Assets

`assets/` stays at the top level. It is not a layer: it is a pool of binary resources, sorted into subfolders by file type (`images/`, `audio/`; a new type gets its own folder) rather than by which config uses a file, that is never applied to the home directory and takes no part in the override order. Configs refer to files in it by absolute path, which templates fill in from `.chezmoi.workingTree` at apply time, so one image can be used from several places without duplication. The zshrc template exports `DOTFILE_REPO_PATH` from the same value for runtime shell code (see "`DOTFILE_REPO_PATH` and applied code" below). Today `assets/images/` holds the fox images (Firefox: `fox-question.png`, `fox-exclamation.png`), the wallpapers used by `fehbg` (`spiderman_artwork.jpg`, `spidey_sense.png`, `spiderman_miles_swinging.jpg`), and `arc_reactor_1920x1200.png` (used by `i3-config`); `assets/audio/` holds `ding.wav` (sound hooks). Code that lives in `assets/` today moves to the layer that uses it: `next_available_ws.sh` and `tzupdate.py` go to `linux/`. Every `/home/steven/...` or `/Users/steven/...` literal pointing at an asset becomes a template-filled path.

### `DOTFILE_REPO_PATH` and applied code

Shell code now lives in two places, and the two must not be confused. Applied code (`functions/`, `scripts/`) is copied by chezmoi to `~/.local/share/dotfiles/functions/` and `~/.local/share/dotfiles/scripts/` (no further subfolders, file names unchanged, for example `functions/play-sound.sh`) and is what the shell runs. Repo content that is never applied (`assets/`, `templates/`, `archive/`) is read from the repo checkout. `DOTFILE_REPO_PATH` always means the repo checkout (`~/dotfiles`) and is used only to reach repo-only content: `template` and `backup.sh` read `$DOTFILE_REPO_PATH/templates/`, and configs reach `assets/` by path. Shell code must never use `DOTFILE_REPO_PATH` to find `functions/` or `scripts/`; the loader (`source-all-functions.sh`), `run_script` and `list-commands.sh` read the applied directories instead.

The zshrc template is the single place that sets `DOTFILE_REPO_PATH` (filled from `.chezmoi.workingTree`, exported before anything is sourced); the `export DOTFILE_REPO_PATH=...` line is removed from `init-env-vars.sh`, and the zshrc template sources `init-env-vars.sh` from the applied scripts directory. Consequence (user accepted): `init-env-vars.sh` cannot be run on its own without `DOTFILE_REPO_PATH` already set. This must be documented in the README and CLAUDE.md: what `DOTFILE_REPO_PATH` means, the applied-versus-repo split, that the zshrc template is where it is set, and that scripts depending on it expect to run from a shell that has loaded `~/.zshrc`. Hardcoded `$HOME/dotfiles/...` and `/home/steven/dotfiles/...` literals in shell code (`zshrc`, `notify.sh`, `tzupdate.sh`) become template-filled or `DOTFILE_REPO_PATH`-relative paths, as the OS-handling section already requires.

The variable is renamed from `DOTFILE_DIR` to `DOTFILE_REPO_PATH` (user decision) so the name says it is the repo path and cannot be mistaken for the applied-code location. The rename is part of this work, not optional cleanup, and no reference to the old name may remain at the end. As of 2026-11-06 the old name appears in: the repo's `CLAUDE.md`, `functions/source-all-functions.sh`, `functions/template.sh`, `functions/run-script.sh`, `scripts/backup.sh`, `scripts/init-env-vars.sh` and `scripts/list-commands.sh`, plus `functions/dotbot.sh`, which is deleted at migration anyway. Verify with a repo-wide search for `DOTFILE_DIR` (excluding `archive/` and git history). Also check the user's `~/.zshrc.local` and any Claude skill or global instruction outside the repo that mentions it, and report those to the user instead of editing them silently. `SOURCE_ALL_FUNCTIONS` keeps its name, but its value now points at the applied loader.

### Files are copies; merging and drift

Every chezmoi target is a real file, not a symlink. Files that cannot include other files (Claude `settings.json`, VS Code `settings.json`) are generated by merging the layers' fragments. Fragments are strict JSON, one file per layer under `layers/<layer>/<tool>/`; a missing layer file is skipped. One shared template in `home/.chezmoitemplates/` does the merge using chezmoi's built-in `jq` template function (no external jq dependency): objects deep-merge, arrays concatenate and de-duplicate, scalars take the most specific layer's value. Sprig's `mergeOverwrite` is not enough because it replaces arrays. There is no remove syntax; anything that should not apply everywhere belongs in a group or machine layer instead of `shared`. In Claude permissions, `deny` still wins over `allow`. `vscode/settings.json` is JSONC and has one real `//` comment (line 58 of the old file); fragments cannot hold comments, so that comment moves into the template as a template comment and does not appear in the generated file.

Merge-template facts (checked against the chezmoi v2.74.0 docs and by running it). The `jq` template function has the signature `jq query input` (query first, so `$docs | jq $prog` works), is backed by the gojq library (no external `jq` binary), and returns a LIST of results, so the merge template must take `first`. gojq differs slightly from the `jq` binary in edge cases, so test the merge program against gojq. jq's `*` operator replaces arrays, and gojq has no `keys_unsorted`. A working merge program, verified in the sandbox, is a recursive `def merge($a; $b)` that merges objects by `keys`, concatenates arrays followed by an order-preserving de-duplication (`reduce .[] as $x ([]; if any(.[]; . == $x) then . else . + [$x] end)`), and lets the later scalar win; with it three test layers produced the expected union of `allow` entries (de-duplicated), the later `env`/`model` values, and the macOS-only `hooks`. The program is settled and re-verified with `chezmoi execute-template` (gojq) on 2026-11-06: it is kept in `home/.chezmoitemplates/` exactly as below and is applied to a list of the layer documents ordered least to most specific, then `first` is taken. The template must also map `darwin` to the `macos` layer directory (see "Repo layout").

```
def dedup: reduce .[] as $x ([]; if any(.[]; . == $x) then . else . + [$x] end);
def merge($a; $b):
  if ($a|type) == "object" and ($b|type) == "object" then
    reduce (($a|keys) + ($b|keys) | unique)[] as $k ({};
      .[$k] = (if ($a|has($k)) and ($b|has($k)) then merge($a[$k]; $b[$k])
               elif ($b|has($k)) then $b[$k] else $a[$k] end))
  elif ($a|type) == "array" and ($b|type) == "array" then ($a + $b | dedup)
  else $b end;
reduce .[1:][] as $l (.[0]; merge(.; $l))
```

Output keys come out sorted (gojq), which is harmless for settings files.

It is local scope and is read only in sessions started with the home directory itself as the working directory. Anything that must apply in every project (permissions, `additionalDirectories`, `enabledPlugins`) belongs in `~/.claude/settings.json`. The existing `add-allowed-directory.sh` writes to `~/.claude/settings.local.json`, so its entries only take effect in sessions started in `~`; `~/.claude/settings.json` is generated in this design, so such directories must come from a layer fragment. Drift handling is chezmoi's own, and the user decided it should prompt: if the live file differs from what chezmoi last wrote (including when Claude Code itself edits the generated `~/.claude/settings.json`; the verified sources of such drift are `/config`, `/model`, `/fast`, `/advisor` and user-scope plugin install, whereas an "always allow" approval writes the project's `.claude/settings.local.json`, not the user file), chezmoi shows a diff and asks before overwriting, and the user folds any change worth keeping into the right `layers/` fragment. Silent overwrite is explicitly not wanted. Non-interactive runs (including Claude's) should use `--error-on-conflict` (exit with an error instead of prompting); `--force` skips the prompt and overwrites, so it is not used for routine applies. Verified by running chezmoi v2.74.0 on macOS: editing a managed file and re-applying with no TTY and no flags prints "has changed since chezmoi last wrote it?" then fails with `could not open a new TTY` (exit 1) and leaves the edited file untouched; `apply --error-on-conflict` exits 1 and leaves it untouched (it prints nothing beyond the config warning, so callers must check the exit code); `apply --no-tty` reads the answer from stdin (valid answers are `diff/overwrite/all-overwrite/skip/Skip-conflicts/quit`, and EOF is an error); `apply --force` silently overwrites. There is no sync-back step in this version; the docs say to edit with `chezmoi edit` (or in `home/` and `layers/` directly) and then apply. `chezmoi re-add` exists for pulling a live edit back into non-template files and may be mentioned in the docs, but it does not work for templates.

### Firefox

`userChrome.css` becomes a template with the five fox-image paths rendered from the working tree's `assets/images/`. A `run_onchange_after_` script in `.chezmoiscripts/` finds the profile: base directory by OS (`~/Library/Application Support/Firefox/` on macOS, `~/.mozilla/firefox/` on Linux), then in `profiles.ini` the `Default=` of the `[Install…]` section (the profile this install actually uses; the `Default=1` flag on a profile is legacy and wrong on this Mac), falling back to the profile flagged `Default=1`. ### Secrets

Secrets live in Bitwarden and are read at apply time by `bw` template functions (`bitwarden`, `bitwardenFields`). `home/private_dot_zshrc.local.tmpl` renders `~/.zshrc.local` (mode 600) from vault items; variables that only a group needs (for example the Atlassian token and email, Bedrock-related secrets) are guarded by the group value, so a personal machine never sees work variable names or items. The full, detailed Dimer `autoMode.environment` text lives in a Bitwarden secure note and is pulled in by the Claude settings template; the tracked work fragment carries only a sanitized generic version. This replaces the earlier untracked `*.local.json` fragment idea and the per-layer `zshrc.local.template` mechanism. Non-secret machine/work environment (AWS profile name, region, model IDs, PATH entries) lives in tracked `layers/.../zsh/env.zsh` fragments. `.claude/settings.local.json` is untracked (already gitignored; the tracked copy was removed from the index during cleanup). The vault items and field names the templates expect are listed in the README so they can be created by hand before the first apply. Failure policy (author's calls): a real apply aborts, writing nothing, if the vault is locked, `BW_SESSION` is unset, or an item a machine's group needs is missing; items for other groups are never referenced, so their absence is not an error. Dry-runs and verification renders use an explicit placeholder switch (an environment variable that makes secret-bearing templates emit obvious placeholders); the templates refuse to render with the switch set when the destination is the real home directory, so placeholders can never be written to a live file. As a consequence, verification renders can compare everything except secret-sourced values (for example the full `autoMode` text), and the user performs the final check of those after unlocking. Apply also aborts, before writing anything, if the `~/Archive` folder structure has not been set up (user decision): a `run_before_` check looks for the top-level folders that `init-archive` creates and, if they are missing, stops with a message to run `run_script init-archive ~/Archive`. `install.sh` runs `init-archive` itself before the first apply so a brand-new machine does not deadlock on this check (author's call). The live Archive uses `04_Projects` (underscore), as do the `find` skill, `find-branch.sh` and `claude/CLAUDE.md`, while `scripts/init-archive.sh` creates `04 Projects` (space); the underscore name is canonical (author's call) and `init-archive.sh` must be fixed to match. `~/.claude` pointing at `/Volumes/External/Caches/claude` is specific to the `wMac01` machine (user decision) and is not checked by apply.

Verified chezmoi behavior behind the failure policy and the placeholder switch. There is no dry-run template variable, and templates (including `bitwarden` calls) still execute under `-n`, so the spec's own placeholder environment variable is the right mechanism. The `env` template function returns an empty string for an unset variable, so `{{ if env "BW_SESSION" }}` works as the placeholder-switch test. A missing `bw` executable makes the whole apply abort with a template error and nothing is written or run. Not yet exercised: `bitwarden` against an installed-but-locked vault or a missing item (`bw` is not installed on this Mac), so the builder must test those two cases once `bw` is installed.

### Bitwarden vault layout

Defined from an inventory of the live `~/.zshrc.local` and `~/.claude/settings.json` on `wMac01` (2026-11-06; values not recorded here). The README lists the same items so they can be created by hand before the first apply.

Organization. All items live in one Bitwarden folder named `dotfiles` (folders are only for tidiness; chezmoi looks items up by name and never by folder). Item names follow `dotfiles/<group>/<purpose>`, where `<group>` is exactly the chezmoi `group` value (`work/Dimer_Health`, `personal`), so a template builds the name as `printf "dotfiles/%s/atlassian" .group`. Rules: every name is unique across the whole vault, and no name is a substring of another (`bw get item` searches by name and errors on more than one match); the builder confirms the slash-containing names work once `bw` is installed and falls back to a hyphenated scheme if not. Field names are lowercase snake_case, chosen to describe the value rather than the environment variable that receives it, so the variable names live only in the templates. Templates read them with `bitwarden` (Login `username`/`password`, secure-note `notes`) and `bitwardenFields` (custom fields). Machine layers have no items of their own today; a machine-specific secret would be named `dotfiles/<group>/<machine>/<purpose>`.

### Install and the apply wrapper

`install.sh` (user decision, macOS only for now). It installs chezmoi and the `bw` CLI with `brew install chezmoi bitwarden-cli`, skipping anything already installed. If `brew` is missing it stops with a clear message instead of installing Homebrew. It then runs `init-archive` (see "Secrets") and `chezmoi init --apply` with `--source ~/dotfiles`, and it clones the repo to `~/dotfiles` first on a brand-new machine. It branches on OS: `darwin` runs the steps above; Linux is a stub that exits with a "not implemented" message; any other OS exits with a message.

Linux install is out of scope for now (user decision), because it needs verification on the real device. Decided (user): `install.sh` has a Linux branch that is a stub; the real Linux route is implemented when `sLaptop2` is tackled. Until then the "A new machine can be set up by installing chezmoi and `bw`" anti-goal is verified on macOS only, consistent with "Linux" under "Migration and rollback".

The apply wrapper is a shell function named `dotapply` (user decision; it replaces `dotbot`, which is deleted) in `functions/dotapply.sh`. In order, it: pulls the repo with `git -C "$DOTFILE_REPO_PATH" pull`; aborts with a message if `BW_SESSION` is unset (the same policy as "Secrets"); runs a plain `chezmoi apply` so drift prompts as decided under "Files are copies; merging and drift"; and runs `omz reload`. It takes a `--headless` flag for non-interactive callers such as Claude, which needs no Bitwarden session. With `--headless`, `dotapply`: skips the `git pull` (it applies the local checkout as is); skips the `BW_SESSION` check; sets the environment variable `DOTFILES_HEADLESS=1` for the `chezmoi` call; runs `chezmoi apply --error-on-conflict` instead of the plain apply (exit with an error rather than prompt; callers must check the exit code); and skips `omz reload`. It is a separate mechanism from the placeholder switch in "Secrets": headless writes real files to the real home directory and never emits placeholders. Templates handle `DOTFILES_HEADLESS` as follows, and no template calls `bitwarden` or `bitwardenFields` when it is set: `private_dot_zshrc.local.tmpl` is ignored by `.chezmoiignore`, so `~/.zshrc.local` is left untouched; the Claude settings template takes `autoMode.environment` from the live `~/.claude/settings.json` (read with `include` on the absolute path) instead of the `claude-auto-mode` note, and if the live file is missing or has no `autoMode.environment` on a group that uses the note, the apply aborts, writing nothing, with a message to run `dotapply` with the vault unlocked first. A headless apply never changes any secret-sourced value. The `omz-install.sh` step is dropped because the `.chezmoiexternal.toml` externals replace it. It never passes `--force`. The function lives in the applied `functions/` directory, so on a brand-new machine the first apply comes from `install.sh`, not from `dotapply`.

### Migration and rollback

The chezmoi source directory stays `~/dotfiles` on every machine (set with `--source`/`sourceDir`; `install.sh` clones to `~/dotfiles` on a new machine), so the absolute asset paths baked into configs, `DOTFILE_REPO_PATH`, and rollback all refer to one stable location. The worktree below exists only while building; at cutover branch `v1-v2-migration` is merged and `~/dotfiles` is updated in place, then the worktree is removed (author's call). Because live symlinks point into `~/dotfiles`, restructuring in place would break this Mac's live Claude config. And if `~/.claude/skills`, `hooks`, `scripts` or `CLAUDE.md` are still whole-directory or file symlinks into the repo when chezmoi first applies, chezmoi replaces them with real directories rather than writing through them (see "Directory symlinks" below), which is why the migration script removes them first anyway. So: (1) build in a separate git worktree (for example `~/dotfiles-chezmoi` on a branch) while `~/dotfiles` and every live link stay untouched; (2) reconcile drift first by diffing the live `~/.claude/settings.json` against the repo copy, with the live file backed up before anything else — the `autoMode` block goes to Bitwarden plus a sanitized fragment and the iTerm hooks go to `layers/macos/` (see "Live state on this Mac" below); (3) verify without touching home by running `chezmoi apply --dry-run` and a real apply into a scratch destination such as `/tmp/fakehome`, and comparing the generated Claude `settings.json` to the live one with `jq -S` (the flags a scratch apply needs are listed under "Verification mechanics" below); (4) a `run_once_before_` migration script removes every symlink under `~` that points into the dotfiles repo, backs up any real file it is about to replace into `~/.dotfiles-migration-backup/<timestamp>/`, writes a manifest of the old links, and, on `wMac01` only, replaces the `~/.claude` link (it points at the external drive) with a real directory holding the external contents, as described under "Directory symlinks"; otherwise it runs identically on this Mac and on `sLaptop2`; (5) cutover is run by the user after reviewing the dry-run: merge the branch, unlock Bitwarden, run `install.sh`, and the same on `sLaptop2` after pulling (until then that machine's links stay valid at the old commit); (6) rollback is checking out tag `v1_last`, restoring files from the migration backup, and running the old `./install` (the Dotbot submodule is in that commit). These steps are written into the README.

Live state on this Mac. `~/.claude` is a symlink to `/Volumes/External/Caches/claude`. The live `~/.claude/settings.json` is a regular file that has drifted from the repo copy: it contains the `autoMode` block and iTerm2 hooks, while the repo copy has `ios-simulator-skill`. The migration must reconcile these before overwriting anything — never lose the live content.

Directory symlinks (IMPORTANT correction found by sandbox testing). Chezmoi does NOT write through a directory symlink. When the source manages files under a directory that is a symlink in the destination (tested with a plain directory and with a dot-directory), chezmoi replaces the symlink with a real directory holding only the managed files, silently and with or without `--force`; the old link target (and anything in it) is left untouched but is no longer reachable from that path. For `~/.claude/skills`, `hooks`, `scripts` and `CLAUDE.md` this removes the fear of writing into the old repo directories (the old repo directories would not be modified), but the migration script still removes those links first because it keeps the result deterministic. For `~/.claude` itself on `wMac01`, applying would replace the `~/.claude` → `/Volumes/External/Caches/claude` link with a real directory. Decided (user): this is a one-time migration and the real directory is the intended end state. The migration script, run with no Claude session open, (1) copies the full contents of `/Volumes/External/Caches/claude` into a backup under `~/.dotfiles-migration-backup/<timestamp>/`, (2) removes the `~/.claude` link and creates a real `~/.claude` holding the external contents, and (3) hands off to the normal `install.sh` apply, which then manages the Claude files in it with no special route. Deleting the backup copies and the old external directory is a manual step the user takes after verifying the apply; neither the script nor the apply deletes them. Claude is not needed during the install. Test the script in the sandbox with a symlinked `.claude` first.

Verification mechanics. `--destination`, `--dry-run` ("the destination directory is never modified"), `--persistent-state`, `--source`, `--working-tree`, `--force`, `--no-tty`, `--less-interactive` and `--error-on-conflict` are global flags. A real apply into a scratch `--destination` still runs scripts (including the migration script, which acts on the real `~`) and writes the real persistent state, so scratch applies must pass `--persistent-state <temp file>` and `--exclude=scripts` (confirmed by running it). `apply -n` does not run scripts, and `apply --exclude=scripts` skips them without recording them as run (a later normal apply runs them). Scripts run with the real `HOME` of the invoking environment, not the scratch destination, which is why a scratch apply must always pass `--exclude=scripts`.

Linux. The Linux machine can only be applied when the user is on it. Linux is verified only by the user running `install.sh` on `sLaptop2`; it is not rendered or checked on the Mac.
