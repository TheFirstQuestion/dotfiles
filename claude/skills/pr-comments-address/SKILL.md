## Address PR Comments (Execution)

Implement the changes described in a plan file generated by `/pr-comments-plan`.

### Step 1 — Verify prerequisites

Run this exact command and stop with a clear error if it fails:

```bash
gh --version
```

If `gh` is not installed or the command fails, output:

> **Error:** GitHub CLI (`gh`) is not installed or not on PATH. Install it from https://cli.github.com and run `gh auth login` before using this command.

Then stop. Do not proceed.

### Step 2 — Resolve the plan file

The argument passed to this command is: `$ARGUMENTS`

- If `$ARGUMENTS` is a file path (e.g. `./temp/pr-285-plan.md`), read that file.
- If `$ARGUMENTS` is empty or not a valid path, output:

  > **Error:** No plan file specified. Run `/pr-comments-plan` first to generate a plan, then pass the path here:
  > `/pr-comments-address <REPO_ROOT>/temp/pr-<number>-plan.md`
  >
  > where `<REPO_ROOT>` is the output of `git rev-parse --show-toplevel`.

  Then stop.

Read the plan file and extract:

- The PR number from the `# PR #<number>` heading
- The branch name from the `**Branch:**` line
- Each `## Comment [N/total]` section with its comment ID, file path, location, proposed change bullets, and suggested reply draft

### Step 3 — Confirm the plan

Print a summary of what will be done:

```
## Execution Plan Summary

PR: #<number>  Branch: <branch>
Comments to address: <N>

  [1] <path>  —  <location>
  [2] <path>  —  <location>
  ...
```

Then ask:

> **Ready to implement?** Reply `yes` to begin, or `no` to stop here.

**Do not make any code changes until the developer replies `yes`.**

If `no`, output:

> Stopped. Re-run this command when ready.

Then stop.

### Step 4 — Register TODO items

Use `TaskCreate` to register one task per comment section:

```
TODO [N]: <path> — <location>
  Plan: <first bullet of Proposed change>
```

Mark each task **in_progress** when you start it and **done** when it is complete.

### Step 5 — Implement each comment

Work through the TODO items **one at a time** (sequential by default; see Step 6 for parallelism).

For each comment section in the plan:

#### 5.1 — Refresh structural context

Before touching the file, use code-review-graph MCP tools to verify current state. **Always use these tools for codebase navigation — never grep or find:**

- `mcp__code-review-graph__semantic_search_nodes_tool` — confirm the function/class named in **Location** still exists and find its current line range
- `mcp__code-review-graph__get_impact_radius_tool` — check whether the proposed change affects callers beyond what the plan noted
- `mcp__code-review-graph__query_graph_tool` with `pattern: "tests_for"` — confirm test coverage hasn't changed
- `mcp__code-review-graph__get_review_context_tool` — call with the file path to get full architectural context before making any edit

Fall back to `Read` with a specific line range only for exact line content the graph cannot provide. Never use `Grep` or `Bash(grep)` or `Bash(find)` for codebase exploration.

#### 5.2 — Apply the change

Follow the **Proposed change** bullets from the plan exactly. If the plan's **Inline comment to add** field contains a drafted comment (not "none"), add it to the code at the relevant location as part of this change.

**Mandatory conventions** (checked automatically at Step 7):

- Follow every rule in `.claude/rules/`
- Match the `BaseController` / `BaseService` / `BaseRepository` contracts for any method added or modified.
- Use TypeBox schemas for any new request/response shapes.

If the **Convention notes** section of the plan flagged a conflict between the reviewer's suggestion and a project rule, follow the project rule, not the suggestion, and note the deviation in the reply draft.

#### 5.3 — Read only what is needed

Use `get_review_context` (MCP) or targeted `Read` with a line range. Do not read entire files unless the plan's context excerpt is insufficient.

### Step 6 — Parallelism (optional)

If the plan's **Parallelism recommendation** section says certain comments can be addressed concurrently (no overlapping files), you may handle those as parallel sub-tasks. Comments that share a file must remain sequential — edits shift line numbers.

### Step 7 — Lint check

After all TODO items are marked done, run:

```bash
pnpm lint:fix
```

If lint exits with errors, fix them before proceeding. Re-run until it passes cleanly.

### Step 8 — Post reply drafts

For each implemented comment, post the **Suggested reply draft** from the plan. The correct endpoint depends on whether the comment is inline or issue-level.

Retrieve `{owner}/{repo}` from:

```bash
gh repo view --json nameWithOwner --jq .nameWithOwner
```

Retrieve each `<comment-id>` from the plan's `**Comment ID:**` field in the corresponding comment section.

**Inline review comments** (`**File:**` is a real path, not `(general)`):

```bash
gh api repos/{owner}/{repo}/pulls/{pr-number}/comments/<comment-id>/replies \
  --method POST \
  --field body="<reply text>"
```

**Issue-level comments** (`**File:**` is `(general)`):

These are PR issue comments, not review thread comments — they cannot be replied to via the review replies endpoint. Post a new issue comment instead:

```bash
gh api repos/{owner}/{repo}/issues/<PR>/comments \
  --method POST \
  --field body="<reply text>"
```

If posting a reply fails, print a warning but do not abort — continue with remaining replies.

### Step 9 — Update PR description

Before pushing any code, update the PR description to reflect the changes made so that automated code reviewers have accurate context when they run. Invoke the `update-pr-description` skill now, before pushing.

### Step 10 — Verify changes

After lint passes and reply drafts are posted, invoke the `superpowers:verification-before-completion` skill to confirm the changes actually work end-to-end before declaring done. When identifying what to verify, use `mcp__code-review-graph__get_impact_radius_tool` on the changed files to find affected callers and tests — run those specifically rather than the full suite.

### Step 11 — Done

Output:

```
## Implementation Complete

PR #<number>  Branch: <branch>

  ✓ [1] <path> — <location>
  ✓ [2] <path> — <location>
  ...

pnpm lint:fix — passed
Reply drafts posted to PR thread.
Verification complete.
```

Then stop. Do not push or create commits unless the developer explicitly asks.
